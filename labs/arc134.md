## Read this first

### The 3 rules that prevent most mistakes

**Rule 1: Always know WHERE you are typing.** Look at your prompt (the text before the `$`).

| Prompt looks like | You are in | Meaning |
|-------------------|-----------|---------|
| `student_xx@cloudshell:~ (project-id)$` | **Cloud Shell** | Your main workspace. Most commands go here. |
| `student_xx@vm-2:~$` or `student_xx@bigquery-instance:~$` | **Inside a VM** | A different computer. Only run commands here when the step says **INSIDE THE VM**. |

Type `exit` to leave a VM and return to Cloud Shell.

**Rule 2: Copy ONE block at a time.** Paste, press Enter, read the result, then continue. Do not paste everything at once.

**Rule 3: Variables disappear.** If Cloud Shell reconnects or you open a new tab, run **Step 1** again. If a command shows an empty value (like `serviceAccount:` with nothing after it), that is the reason.

## Step 1: Open Cloud Shell and set variables

☁️ **CLOUD SHELL**

1. Click the **Activate Cloud Shell** icon (top right of the console, looks like `>_`).
2. Click **Continue** and **Authorize** on any pop-ups.

### 1.1 Type your zone

> [!IMPORTANT]
> ✏️ **FILL IN: replace `YOUR_ZONE` with your lab's zone from Step 0** (for example `us-west1-c`). Keep everything else. This is the only value you type in the whole guide.

```bash
# ✏️ FILL IN: replace YOUR_ZONE with your zone, like us-west1-c  (no spaces, no quotes)
export ZONE=YOUR_ZONE
```

### 1.2 Set everything else

🔒 **COPY AS IS** (nothing to change):

```bash
# 🔒 COPY AS IS. The region is worked out from your zone automatically.
export REGION=${ZONE%-*}
export PROJECT_ID=$(gcloud config get-value project)

# Safety check: stops you if the placeholder was not replaced
case "$ZONE" in
  YOUR_ZONE|"") echo "❌ STOP: replace YOUR_ZONE in step 1.1 with your real zone, then run 1.1 again." ;;
  *) gcloud config set compute/region $REGION
     gcloud config set compute/zone $ZONE
     echo "✅ Project: $PROJECT_ID | Region: $REGION | Zone: $ZONE" ;;
esac
```

**Expected:** a line starting with `✅` showing your project, region and zone. If you see `❌`, do 1.1 again.

> [!TIP]
> If the project ID is blank, run `gcloud config set project PROJECT_ID_FROM_THE_LAB_PANEL`, then run 1.2 again.

## Task 3: Give `devops` its roles

☁️ **CLOUD SHELL**

The lab asks you to store the service account email in a variable called `SA`:

```bash
# 🔒 COPY AS IS
export SA=devops@${PROJECT_ID}.iam.gserviceaccount.com
echo $SA
```

**Expected:** `devops@your-project-id.iam.gserviceaccount.com`

Now add the two roles. Run these **one at a time**:

```bash
# 🔒 COPY AS IS
gcloud projects add-iam-policy-binding $PROJECT_ID \
  --member="serviceAccount:${SA}" \
  --role="roles/iam.serviceAccountUser" \
  --condition=None
```

```bash
# 🔒 COPY AS IS
gcloud projects add-iam-policy-binding $PROJECT_ID \
  --member="serviceAccount:${SA}" \
  --role="roles/compute.instanceAdmin.v1" \
  --condition=None
```

> [!NOTE]
> **Why `--condition=None`?** The lab project already has a conditional rule. Without this flag, gcloud stops and asks a question. If you see a menu with `[1] [2] [3]`, type **2** (None) and press Enter.

**Check it worked:**

```bash
# 🔒 COPY AS IS
gcloud projects get-iam-policy $PROJECT_ID \
  --flatten="bindings[].members" \
  --filter="bindings.members:${SA}" \
  --format="table(bindings.role)"
```

**Expected:** both `roles/iam.serviceAccountUser` and `roles/compute.instanceAdmin.v1` appear.

Click **Check my progress** for Task 3.

### Part B: Test its permissions (the lab asks for this)

Press **Enter** at every question (passphrase prompts). Type `y` if asked to continue. A message like `Updating project ssh metadata...failed` is normal.

# 🔒 COPY AS IS (inside vm-2). The VM finds its own zone, so there is nothing to type.

**Expected:** a list showing `vm-2`, your zone printed, then `test-vm` gets created. This proves the service account's permissions work. If it says `test-vm` **already exists**, that is fine: the check is already done.

## Task 5: Create a custom role from a YAML file

☁️ **CLOUD SHELL** (NOT inside a VM. A VM cannot create roles, and its `PROJECT_ID` variable is empty.)

> [!CAUTION]
> 🛑 Check the prompt says `@cloudshell`. If it says `@vm-2`, type `exit` first.

Confirm the variable is set:

```bash
# 🔒 COPY AS IS
echo $PROJECT_ID
```

If it prints nothing, run Step 1 again.

Create the YAML file:

```bash
# 🔒 COPY AS IS
cat > role-definition.yaml <<EOF
title: "Cloud SQL Custom Role"
description: "Connect to and get Cloud SQL instances"
stage: "ALPHA"
includedPermissions:
- cloudsql.instances.connect
- cloudsql.instances.get
EOF
```

Create the role:

```bash
# 🔒 COPY AS IS
gcloud iam roles create cloudsqlcustomrole --project=$PROJECT_ID --file=role-definition.yaml
```

**Expected:** `Created role [cloudsqlcustomrole].`

Verify:

```bash
# 🔒 COPY AS IS
gcloud iam roles describe cloudsqlcustomrole --project=$PROJECT_ID
```

Both `cloudsql.instances.connect` and `cloudsql.instances.get` should be listed.

Click **Check my progress** for Task 5.

## Task 6: BigQuery from a service account

> [!NOTE]
> The lab text makes this task look like only code, but its check **verifies that the VM exists and uses the `bigquery-qwiklab` service account.** So do Part A and Part B fully.

### Part A: Create the service account and give it roles

☁️ **CLOUD SHELL**

```bash
# 🔒 COPY AS IS (if it says "already exists", that is fine)
gcloud iam service-accounts create bigquery-qwiklab --display-name="bigquery-qwiklab"
export BQ_SA=bigquery-qwiklab@${PROJECT_ID}.iam.gserviceaccount.com
echo $BQ_SA
```

Add the two roles, one at a time:

```bash
# 🔒 COPY AS IS
gcloud projects add-iam-policy-binding $PROJECT_ID \
  --member="serviceAccount:${BQ_SA}" \
  --role="roles/bigquery.dataViewer" \
  --condition=None
```

```bash
# 🔒 COPY AS IS
gcloud projects add-iam-policy-binding $PROJECT_ID \
  --member="serviceAccount:${BQ_SA}" \
  --role="roles/bigquery.user" \
  --condition=None
```

### Part B: Create the VM

☁️ **CLOUD SHELL**

```bash
# 🔒 COPY AS IS
gcloud compute instances create bigquery-instance \
  --zone=$ZONE \
  --machine-type=e2-medium \
  --service-account=$BQ_SA \
  --scopes=https://www.googleapis.com/auth/cloud-platform
```

Click **Check my progress** for Task 6 now. This should pass.

**Check that the VM uses the right service account:**

```bash
# 🔒 COPY AS IS
gcloud compute instances describe bigquery-instance --zone=$ZONE \
  --format="value(serviceAccounts[0].email)"
```

**Expected:** `bigquery-qwiklab@your-project-id.iam.gserviceaccount.com`

| What you see | What to do |
|--------------|------------|
| The `bigquery-qwiklab@...` email | Perfect. Go to Part C |
| A different email (like `...-compute@developer.gserviceaccount.com`) | The VM has the wrong account. Delete it and create it again: `gcloud compute instances delete bigquery-instance --zone=$ZONE --quiet`, then run the create command above |
| `already exists` when creating | The VM is already there. Run the check above to confirm it has the right account |
| `not enough resources` | See Troubleshooting |

### Part C: Run the query (the lab asks for this)

☁️ **CLOUD SHELL** (connect to the VM):

```bash
# 🔒 COPY AS IS
gcloud compute ssh bigquery-instance --zone=$ZONE
```

> [!CAUTION]
> 🛑 Everything below runs 🖥️ **INSIDE THE VM**. Check the prompt says `@bigquery-instance` before you continue. Do **not** run the install commands in Cloud Shell.

Install the tools. A virtual environment avoids a common Debian error:

```bash
# 🔒 COPY AS IS (inside bigquery-instance)
sudo apt-get update
sudo apt-get install -y python3-pip python3-venv
python3 -m venv ~/venv
source ~/venv/bin/activate
pip install google-cloud-bigquery pyarrow pandas db-dtypes
```

After this, the prompt starts with `(venv)`.

The VM looks up its own project ID and service account, so you do not type them:

```bash
# 🔒 COPY AS IS (inside bigquery-instance)
export PROJECT_ID=$(curl -s -H "Metadata-Flavor: Google" http://metadata.google.internal/computeMetadata/v1/project/project-id)
export BQ_SA=$(curl -s -H "Metadata-Flavor: Google" http://metadata.google.internal/computeMetadata/v1/instance/service-accounts/default/email)
echo $PROJECT_ID $BQ_SA
```

**Expected:** your project ID and `bigquery-qwiklab@...`. If the second value is a `...-compute@developer...` address, this VM has the wrong service account, so go back to Part B.

Create the Python file. The `sed` line fills in your values automatically, so you do not edit `YOUR_SERVICE_ACCOUNT` or `YOUR_PROJECT_ID` yourself:

```bash
# 🔒 COPY AS IS (inside bigquery-instance). Do not edit the YOUR_... words, sed replaces them.
cat << 'EOF' > query.py
from google.auth import compute_engine
from google.cloud import bigquery
credentials = compute_engine.Credentials(
    service_account_email='YOUR_SERVICE_ACCOUNT')
query = '''
SELECT name, SUM(number) as total_people
FROM `bigquery-public-data.usa_names.usa_1910_2013`
WHERE state = 'TX'
GROUP BY name, state
ORDER BY total_people DESC
LIMIT 20
'''
client = bigquery.Client(
    project='YOUR_PROJECT_ID',
    credentials=credentials)
print(client.query(query).to_dataframe())
EOF
sed -i "s/YOUR_SERVICE_ACCOUNT/${BQ_SA}/; s/YOUR_PROJECT_ID/${PROJECT_ID}/" query.py
```

Check the words were replaced (you should see your real values, not `YOUR_...`):

```bash
# 🔒 COPY AS IS (inside bigquery-instance)
grep -n "bigquery-qwiklab\|qwiklabs-gcp" query.py
```

Run it:

```bash
# 🔒 COPY AS IS (inside bigquery-instance)
python3 query.py
```

**Expected:** a table of 20 Texas names with totals.

Type `exit` to return to Cloud Shell, then click **Check my progress** for Task 6 again if it was not green.

## Troubleshooting

| What you see | Why | Fix |
|--------------|-----|-----|
| `❌ STOP: replace YOUR_ZONE` | The placeholder was not replaced | Do Step 1.1 again with your real zone, then 1.2 |
| `Permission denied on 'locations/your_zone'` | A placeholder like `YOUR_ZONE` was typed literally | Use your real zone, or the zone-lookup command in Task 4 Part B |
| `project property is set to the empty string` | You ran the command **inside a VM** | Type `exit`, run it from Cloud Shell |
| `not enough resources ... Try a different zone, or try again later` | That zone is out of capacity for the machine type | Wait a minute and retry. If it still fails, switch to another zone in the same region (for example `export ZONE=us-west1-b`) and run the create command again. Later commands use `$ZONE`, so they follow your change |
| `... already exists` (VM or service account) | You created it before | Skip it and continue. For a VM, run the `describe` check to confirm its service account |
| Menu with `[1] [2] [3] Specify a new condition` | IAM policy has a condition | Type **2** (None), or add `--condition=None` |
| Empty value like `serviceAccount:` | Variables were lost | Re-run Step 1 (and re-run the `export SA=` or `export BQ_SA=` line) |
| `externally-managed-environment` error with pip | Debian blocks system-wide pip | Use the virtual environment commands in Task 6 Part C |
| `ModuleNotFoundError` inside the VM | The virtual environment is not active | Run `source ~/venv/bin/activate`, then try again |
| `Access Denied` or 403 from BigQuery | The service account is missing a role | In Cloud Shell, add `roles/bigquery.dataViewer` and `roles/bigquery.user` with `--condition=None` |
| `grep` still shows `YOUR_...` in `query.py` | The VM variables were blank when `sed` ran | Redo the metadata step, then the `sed` line |
| Check says "create an instance using the service account" | VM missing or wrong service account | Run the `describe` command in Task 6 Part B |
| Check my progress still red | Checker can be slow | Wait 20 seconds, click again |
| SSH asks for a passphrase | Normal first-time setup | Press Enter twice |
